# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

WsCore is a real-time multiplayer game server: a .NET 10 / ASP.NET Core WebSocket backend and a TypeScript (Vite) client, joined by a shared MemoryPack binary protocol. The client is a **unified single-socket app**: one `WsClient` (one WebSocket) lives the whole session, and the Discord-style lobby (text chat) and the 3D Three.js scene are **UI states** of one shell, not separate apps. (Roadmap stage 2 replaced the old 2D-Phaser / 3D / lobby split; see `.plans/`.)

## Repository layout

- `WsServer/WsServer/` — the entire server (one project; older docs describe it as several). Notable folders:
  - `Shared/` — transport-agnostic infrastructure: `MessageSerializer`, `ReflectionServerLogicProvider`, `GameMessenger`, `ConnectionManager`, `Rooms/`, `StaticFileCaching`, and `Shared/Abstract/` interfaces.
  - `Sessions/` — `SessionManager` + `ClientSession`: per-connection identity (name, slots, chat rate limit) and every room transition, incl. spawning/removing the game avatar (see [Runtime architecture](#runtime-architecture)); `UserDirectory` + `UserAccount`: the stable users behind connections, presence (online / away / offline) and accounts (a user's keys, login + password hash, profile); `PasswordHasher` (PBKDF2); `AvatarImage` (upload validation + the `/avatars/{userId}` endpoint).
  - `Chat/` — `ChatHistoryService`: message ids, the per-room in-memory history window, history paging.
  - `Persistence/` — `IChatStorage` (`SqliteChatStorage` / `NullChatStorage`): durable chat history + known users behind one write-behind worker thread.
  - `Game/Core/` — game simulation (`GameModel`, `Player`, `Bullet`, `World/`).
  - `Game/Protocol/{Domain}/` — message contracts grouped by domain (`Chat`, `Map`, `Player`, `GameState`, `Bullets`, `Rooms`, `Connection`, `Presence`, `Account`), each with `Requests/`, `Events/`, `Handlers/`.
- `WsServer/WsServer.TestClient/` — a RazorConsole console app that boots an **embedded** server + interactive terminal UI. Run with `dotnet run` for local testing without the browser client.
- `WsCore.Client/src/` — TS client (unified single-socket app):
  - `app/` — the shell: `App` (owns the one `WsClient`, connects once, `lobby`↔`game` state machine, connection banner, reconnect re-init, keeps the stored identity in step with account events), `LobbyState` (drives `LobbyUI` and the profile dialog from client events; no own socket) and `IdentityStorage` (the user key + last name in `localStorage`).
  - `game/` — the Three.js scene (was `3d/`): `GameScene` (scene/camera/renderer/RAF/input + full `exit()` teardown), `Player` (pure state, implements `IPlayer`), `PlayerView` (the sprite/nick visual), `World`, `MapObject`.
  - `lobby/` — `LobbyUI` (rooms, chat, member list with avatars and user cards), `ProfileDialog` (own profile: name, avatar, about, claim / log out) + CSS only (no app logic).
  - `network/` — `WsConnection` (transport: reconnect/backoff, silence watchdog, `connectionStatus`) → `WsClient` (session state: server-driven rooms, server-confirmed joins, players only while in a spatial room, the per-room chat cache and the presence roster; a typed `on()`/`emit()` event emitter), `ChatLog` (the chat cache: pure, unit-tested), `rooms/`, and `network/protocol/` (**generated** — see below).
  - `utils/` — `Emitter`, `Keyboard`, `ChatUI`, `Common`, `SnapshotInterpolation` (tick-snapshot interpolation buffer + server clock), `IdleDetector` (away/afk detection), `AvatarImage` (downsizes a picked picture to the 128×128 JPEG that is uploaded).
  - `main.ts` is a thin entry that builds `App` from the entry form (`#name-form` in `index.html`: quick entry by name, or — via "I have an account" — login + password).
  - `*.test.ts` files sit next to the code they cover (e.g. `network/rooms/RoomManager.test.ts`, `network/protocol/protocol.test.ts`) — see [Testing](#testing).
- `WsServer/WsServer.Tests/` — xUnit project: unit tests for `GameModel`/`RoomManager`/`MessageSerializer`, plus a real-WebSocket integration test in `Integration/` (see [Testing](#testing)).
- `AGENTS.md` (root) and `WsServer/AGENTS.md` — detailed prior guidance on conventions and the room system. Read them for depth; note both predate the single-project merge (see Gotchas).

## Commands

For interactive development, run server and client in **separate terminals**. For **automated testing**, bring the whole stack up in the background with `scripts/dev-up.sh` and drive the browser via the integrated-browser MCP — see [Testing](#testing).

```bash
# Server (http://localhost:5000, WebSocket at /ws, dashboard JSON at /info — connections,
# gamePlayers (avatars incl. the 10 built-in bots), per-room user counts)
cd WsServer/WsServer && dotnet run

# Client (Vite dev server at http://localhost:5001)
cd WsCore.Client && npm install && npm start

# Format TS after changes (required; enforced style)
cd WsCore.Client && npm run format        # or: npm run format:check

# Client production bundle (dist/: index.html + hashed chunks; three.js is a lazy chunk loaded on Play)
cd WsCore.Client && npm run build

# Embedded test client (server + terminal UI in one process)
cd WsServer/WsServer.TestClient && dotnet run

# --- automated testing helpers ---
scripts/dev-up.sh                  # start server + client in background (logs/pids in .run/)
CLIENT_PORT=5199 scripts/dev-up.sh # ...on an alt client port (dodge a stale :5001 service worker)
scripts/dev-down.sh                # stop both (reads the client port from .run/client.port)
```

The client is one app: it opens in the lobby; the **Play** button on a spatial room (the `game` room) enters the 3D scene, **Back to Lobby** returns, and the single WebSocket persists across those switches and across server restarts (auto-reconnect). In dev the client hard-codes the server to port 5000; in production it uses the current origin.

- A **service worker from another localhost project can shadow `localhost:5001`** and serve the wrong app (you'll see a foreign `document.title`). Bring the stack up on a dedicated port — `CLIENT_PORT=5199 scripts/dev-up.sh` — and navigate there; a distinct port is a distinct origin with no stray SW.
- The dev client's `getWebSocketUrl()` always targets `:5000`, so the client port doesn't affect which server it talks to.
- "Back to Lobby" matches **two** divs by `textContent` (the button and its wrapper) — click the last match; the leak check is about that pair not multiplying.
- No browser MCP that can reach this machine's ports? ## Message protocol (the core abstraction)

Every client↔server message is framed as `[TypeId: 1 byte][MemoryPack payload]`.

- A message is a `[MemoryPackable] partial class` implementing **`IClientRequest`** (client→server) or **`IServerEvent`** (server→client), with a `static byte TypeId`. `[GenerateTypeScript]` opts it into TS codegen.
- `ReflectionServerLogicProvider` scans the assembly at startup, registering every `IClientRequest`/`IServerEvent` by its `TypeId` and wiring each request to its handler. **TypeIds must be unique** — a collision throws `DuplicateMessageIdException` at boot (a stale hand-maintained `ServerMessageType.cs` map used to promise this but had drifted out of sync with real ids and was removed; before picking a new id, grep for `TypeId =>` across `Game/Protocol/**` to see what's taken).
- Request handlers subclass `RequestHandlerBase<TRequest>` and are constructed via DI (`ClientRequestHandlerFactory`), so they can inject `IGameMessenger`, `ILogger`, etc.
- `WebSocketHandler` also accepts **JSON text frames** as a debugging fallback (it reflects fields onto the request type by name); the real client always sends binary.

### Adding a new message type

1. Create the class under the right `Game/Protocol/{Domain}/{Requests|Events}/`, mark it `[MemoryPackable]` (+ `[GenerateTypeScript]`), implement `IClientRequest`/`IServerEvent`, assign an unused `TypeId`.
2. For a request, add a `{Name}Handler : RequestHandlerBase<{Name}Request>` in that domain's `Handlers/`. Discovery is automatic — no manual registration.
3. Regenerate client TS types (below), then handle the message in the client's `WsClient`/`WsConnection` layer.

### Regenerating client TypeScript types — non-obvious

The generated files in `WsCore.Client/src/network/protocol/` (readers/writers + model classes) come from MemoryPack's TS source generator, but the generator output is **commented out** in `WsServer/WsServer/WsServer.csproj` (the `MemoryPackGenerator_TypeScriptOutputDirectory` block). The checked-in TS is the source of truth day-to-day. To regenerate after changing a `[GenerateTypeScript]` type, **uncomment that block, build the server, then re-comment it**, and run `npm run format`.

## Runtime architecture

- **A connection is not a player.** Connecting creates a `ClientSession` (name, equipment slots, chat cooldown — `Sessions/SessionManager.cs`) and puts the client in the `lobby` room; a `Player` avatar in `GameModel` (id == clientId) exists only while the client is in a room supporting `RoomCompatibility.Spatial` (the `game` room) and is removed when it leaves that room or disconnects. All room transitions go through `SessionManager.JoinRoom`, which answers the joiner with `JoinRoomResultEvent` (success or failure, before any room state). Scoping: entering the game → the joiner gets `GameStateUpdateEvent`, other spatial members `PlayerJoinedEvent`; leaving/disconnect → `PlayerLeftEvent` to spatial members; shots/slots/respawns/map changes → spatial members (`IGameMessenger.BroadcastToSpatial`); chat → the sender's room only (`BroadcastToRoom`); chat history → the requester; presence → every identified connection (`BroadcastWhere`); `SetPlayerNameEvent` → the client's room (for a client with an avatar: the spatial audience); `RoomUsersUpdateEvent` → the room's members; `RoomListEvent` → pushed to non-spatial clients on any membership change. Game requests (move/target/shoot/respawn/slots/map) from a client without an avatar are no-ops (slots are remembered on the session and applied at spawn).
- **Users and presence.** Client ids change on every (re)connect, so a client that wants a stable identity sends `IdentifyRequest { UserKey, Name }` as its first request (`WsClient` does, with a random key from `localStorage` — `wscore.userKey`; it also sets the name, replacing the old `SetPlayerNameRequest` on init). `SessionManager.Identify` binds the session to a `UserAccount` (`UserDirectory`: key → user, keyed by the key's SHA-256 — the key itself is a bearer secret and is never stored or broadcast; others only see the public `UserId`). A user may have several sessions (reconnect overlap, a second tab). Presence = `Offline` (no sessions) / `Online` (any session active) / `Away` (all sessions idle), plus the room of an active session. **Users are never removed from the member list when they disconnect — they turn offline** (with `LastSeenMs`). The identifying client gets `PresenceSnapshotEvent` (its `UserId`, everyone online, the `PresenceMaxOfflineUsers` most recently seen offline users); after that every identified connection — in any room, lobby or game — gets a `PresenceUpdateEvent` when a user's status / room / name changes (`PublishPresence` diffs against what was last announced). Away is client-driven (`IdleDetector`: 5 min without input → `SetAwayRequest`), so its announcements are rate-limited: the state is applied at once but flushed at most every `PresenceFlushIntervalSeconds` (`SessionManager.FlushPresence`, called each tick). Connections that never identify (LoadTest bots, the TestClient, old clients) stay anonymous: no presence traffic, `UserId` 0 in chat and in `RoomUserInfo`; the lobby lists them as guests while they are in the room (once they have a name).
- **Accounts and profiles.** A user starts as a **guest**: it exists only through the key in one browser. `ClaimAccountRequest { Login, Password }` *claims* it — the same user (id, history, name) gets a login (3–32 of `a-z 0-9 . _ -`, case-insensitive, unique) and a password (≥ 8 chars; PBKDF2-SHA512, `PasswordHashIterations`). `LoginRequest { Login, Password, UserKey }` enters a claimed account from another device: `UserKey` is a fresh key the client made up, which on success becomes one more key of the account (`UserDirectory.BindKey`; a user has any number of keys, one per device) — so every later connect is a plain `IdentifyRequest` with it, and the password is never stored client-side. The client sends it *instead of* identifying (`WsClient.loginOnConnect`); a connection that had identified as a guest leaves that user. `LogoutRequest` unbinds this connection's key (other devices stay logged in; a guest cannot log out — its key is the only way back). Each is answered to the requester with `AccountResultEvent { Action, Success, Error, Login }` (`Error` is an `AccountError` code the client words itself); `PresenceSnapshotEvent.YourLogin` tells an identifying client whether its user is claimed. **Hashing never runs on the tick thread**: `SessionManager` validates on the tick, hashes / verifies on the thread pool and applies the outcome on a later tick (`DeliverCompleted`); one such operation per session at a time (`ClientSession.AuthPending`). Abuse limits: every account/profile request is rate-limited per connection (`AccountRequestCooldownSeconds`), and `LoginMaxFailures` wrong passwords in a row lock that login for `LoginLockoutSeconds` (devices already logged in are unaffected — they use their key). The **profile** — "about" (`UpdateProfileRequest`, `MaxAboutLength` 190) and the avatar — belongs to any identified user, guest or claimed, and travels in `PresenceUserInfo` (`About`, `AvatarVersion`), so it reaches everyone through the usual presence updates. The avatar is uploaded over the socket (`SetAvatarRequest { Image }`: PNG / JPEG / WebP recognised by signature, ≤ `MaxAvatarBytes`; the client sends a 128×128 JPEG; empty = remove), stored as a blob and served by `GET /avatars/{userId}?v={AvatarVersion}` — `immutable` because the version (time-based, never reused) is part of the URL, `nosniff`, content type from the signature. An `IdentifyRequest` with an empty name keeps the user's stored name.
- **Chat history.** Every chat message gets a global, strictly increasing `Id`, a timestamp and its author (`UserId`, name snapshot) in `ChatHistoryService.Append`, which caches it, queues it for the database and returns the `ChatMessageEvent` to broadcast — the live event and the stored message share the id, which is what lets clients merge the two. History is **pulled** by the client for its current room (`ChatHistoryRequest` → `ChatHistoryEvent`): `AfterId` = catch-up (everything after what the client has; a *reset* with the latest page if nothing is cached, the gap exceeds one page, or the `Epoch` differs), `BeforeId` = the page before the oldest message it has (scroll-up). `ChatHistoryPageSize` (50) per page. **Hot path = memory:** the newest `ChatHistoryCacheSize` (200) messages per room live in the service, so joins, reconnect catch-ups and the first scroll-back pages never touch the database; only a `BeforeId` older than that window queries storage — asynchronously on the storage thread, one query per session at a time (`ClientSession.HistoryQueryPending`), the answer delivered on a later tick via `ChatHistoryService.DeliverCompleted`. `Epoch` names the id space: stored in the database (stable across restarts), random per process without persistence — a client seeing a new epoch drops its cached ids.
- **Storage** (`Persistence/SqliteChatStorage`, enabled by `GameServer:ChatDatabasePath`; empty → `NullChatStorage`, nothing persists — the default for tests / LoadTest; a database that cannot be opened logs an error and falls back to it rather than stopping the server). One SQLite connection owned by one background thread fed by a bounded FIFO: the tick thread never does I/O; writes are write-behind and group-committed (everything queued = one transaction; WAL, `synchronous=NORMAL`); a query is ordered behind the appends queued before it, so it always sees them. Paging is keyset (`WHERE room_id = ? AND id < ? ORDER BY id DESC LIMIT ?` on the `(room_id, id)` index — no OFFSET). Users are three tables — `users` (name, last seen, login, password hash, about, avatar version), `user_keys` (key hash → user) and `avatars` (blob) — versioned by `PRAGMA user_version` (a pre-accounts database is migrated on open); avatar reads go through the same queue (`LoadAvatar`, callable from the HTTP thread, bounded by a semaphore so the endpoint cannot crowd out chat writes). Retention: `ChatHistoryMaxMessagesPerRoom` and `UserRetentionDays`, applied at startup and hourly; `MaxKnownUsers` evicts the longest-offline user — both only ever drop **guests**, never a claimed account. Everything is read once at startup (`StorageSnapshot` → history windows + user directory); graceful shutdown stamps last-seen for connected users and flushes the queue (`Dispose`).
- **Client chat cache** (`network/ChatLog.ts`, owned by `WsClient`, one contiguous log per room): kept for the whole page session — across room switches, lobby↔game and reconnects. On every confirmed join `WsClient` sends a catch-up from the room's last cached id, so returning to a room renders instantly from the cache and fetches only what was missed; `loadOlderChat()` extends it backwards (one request at a time, with a timeout so a lost request can be retried). `LobbyState` renders incrementally: `setMessages` on entering a room / reset, `appendMessages` for live messages and catch-ups (follows the bottom only if the user is there or wrote the message — otherwise a "new messages" button), `prependMessages` for older pages with an explicit scroll correction (`overflow-anchor: none` on the list so the browser doesn't apply a second one). The in-game `ChatUI` overlay shows the tail of the same log.
- `GameServer : GameServerBase<GameModel>` owns the fixed **~30 FPS loop** (`PeriodicTimer` at 33 ms). It is a **hosted service** (`IHostedLifecycleService`): the loop starts with the host, and graceful shutdown (SIGTERM/Ctrl+C) closes every socket in `StoppingAsync`, then stops the loop and drops room state in `StopAsync` — no manual `ApplicationStopping` hook. The simulation runs every tick; a `GameTickUpdateEvent` snapshot is sent only every `SnapshotSendEveryTicks`-th tick (default 2 → ~15 Hz; 1 = every tick) via `GameMessenger.BroadcastSpatialUpdates`, which filters recipients by room so only spatial-room members receive movement updates.
- **Tick snapshots are deltas** (`GameTickUpdateEvent`, built on the tick thread): `ServerTimeMs` (sim time, for client interpolation) + `MovementStateData` (`PlayerId`, `X`, `Y`, `AnimationState` byte — 14 B; aim/target/controls/body angle/velocity are no longer replicated) for only the avatars whose position/animation changed within the last `SnapshotRepeatUnchanged + 1` snapshots (default 2 → a stopped avatar's final state is sent 3×), plus a **full snapshot** (every avatar) every `FullSnapshotIntervalSeconds` (1 s; ≤ 0 = always full). Full snapshots go out as **keyframes**: in the latest-wins slot a pending keyframe is replaced only by a newer keyframe, never by a delta, so a client that loses deltas still converges within one full-snapshot period. An avatar absent from a snapshot is unchanged. The one-shot arrays (`DestroyedBulletsIds`, `RespawnedPlayerIds`, `HitPlayersState`) are accumulated over the ticks between snapshots, but still ride the lossy slot (a replaced snapshot loses them; the client currently ignores them). `WsServer.LoadTest` prints tick bytes/sec per spatial client (`--idle 1` = mostly-idle scenario).
- **Client interpolation** (`src/utils/SnapshotInterpolation.ts`, pure + unit-tested): `WsClient` feeds each snapshot into `ServerClock` (server-time estimate from `ServerTimeMs` + arrival time; also estimates the send interval) and each avatar's `PositionBuffer` (`push` for avatars in the snapshot, `hold` for absent ones — no extrapolation; jumps > `TELEPORT_DISTANCE` snap). `GameScene` draws remote avatars at `serverNow − (1.5 × interval + 15 ms)` and our own at `serverNow − (interval + 25 ms)`; velocity (run animation, sprite facing) comes from the interpolated segment. Player input state (`controls`, aim) is client-owned and never overwritten by snapshots.
- **Single-threaded model.** Client requests, connects and disconnects are all queued from socket threads and executed on the tick thread (`GameServerBase` command queue). On connect the client id is reserved atomically and handed to `WebSocketHandler` synchronously (before its receive loop starts); registration, the session, `InitPlayerEvent` (always the client's first message) and the `lobby` auto-join (`JoinRoomResultEvent`, user list, room list) happen on the next tick — no avatar, no game state. A disconnect is queued behind its connect, so a socket that drops early never leaks a session or an avatar. On disconnect `SessionManager` cleans up room membership, removes the avatar (if any) and tells spatial members (`PlayerLeftEvent`).
- Rooms are persistent and defined **only** in `GameServer.InitializeDefaultRooms()`; clients learn them from `RoomListEvent` (id, name, supported modes, persistence, user count). Spatial state is filtered. `GameModel` uses plain collections (tick thread only; only the id generators and `PlayersCount`/`BulletsCount` are safe from other threads) — never mutate it outside the command queue. `RoomManager`/`ConnectionManager` stay concurrent (`/info` and shutdown enumerate connections off-thread).
- **Send path** (`WebSocketHandler`): one sender per socket fed by a reliable bounded FIFO (`IClientConnection.Send`; capacity `WebSocketSendQueueCapacity` — overflow **terminates** the connection rather than dropping an event) plus a single latest-wins slot for the tick snapshot (`SendLatest`, used by `BroadcastSpatialUpdates`; keyframe-aware, see above). Order between them is preserved. WebSocket keep-alive pings (`WebSocketKeepAlive{Interval,Timeout}Seconds`, 15 s each) drop half-open connections server-side. For the client side, every connection gets a tiny `HeartbeatEvent` (TypeId 7) every `HeartbeatIntervalSeconds` (5 s; sent on the tick thread via the reliable path, 0 disables), and `WsConnection`'s watchdog treats ~15 s (`WATCHDOG_TIMEOUT_MS`) without *any* message while `open` as a dead socket → normal reconnect/backoff with the banner. The watchdog opens a fresh grace window when its own timer was suspended (frozen tab / sleep) or the tab becomes visible again, so background throttling doesn't cause reconnect storms.
- **Static files** (`Program.cs` → `StaticFileCaching`): Vite's hashed chunks (`/assets/name-HASH.ext`) are served `Cache-Control: public, max-age=31536000, immutable`, `index.html` `no-cache`; unhashed public assets (`/knight`, `/map`, `/ui`, `/assets/logo.png`) get no explicit Cache-Control.
- Everything is wired by `services.AddGameServer(config)` + `app.UseGameServer()` (`/ws`, `/health`, `/info`, `/avatars/{userId}`; `WsServer/WsServer/GameServerHostingExtensions.cs`), shared by `Program.cs`, the LoadTest, the TestClient and the test fixture. `GameServer` is one singleton exposed as both `IGameServer` and the hosted service.

## Gotchas (things that will bite)

- **Folders ≠ namespaces.** Files under `Game/Protocol/Chat/` live in namespace `Game.ServerLogic.Chat.*`; `Shared/` files are in `WsServer.*` / `WsServer.Abstract.*`; rooms are in `WsServer.Rooms`. Match the existing namespace of neighboring files, not the folder path.
- **The server is one project now** (commit "Merging all server projects into one"). References to separate `Game/`, `WsServer.Shared/`, `WsServer.DataBuffer/`, and `BenchmarkSuite1/` projects in `AGENTS.md` are stale — those are now folders inside `WsServer/WsServer/`. (The `Dockerfile` has been updated to the single-project layout.)
- **Two room enums, now aligned.** The server uses `WsServer.Rooms.RoomCompatibility` (`TextChat`, `Spatial`, `VoiceChat`, `VideoChat`) and the client uses `CommunicationMode` (`TextChat`, `Spatial`, `VoiceChat`, `VideoChat`). Stage 2 collapsed the client's old `Spatial2D`/`Spatial3D` into a single `Spatial`, so they're now 1:1 — but they're still **two separate enums**, keep both in sync when adding a mode. (`RoomCompatibility` is `[Flags]`-marked yet its values aren't powers of two — a known latent bug, unrelated.)
- **Rooms come from the server.** `GameServer.InitializeDefaultRooms` (`lobby`, `voice`, `game`) is the only definition; the client has no room list of its own (`WsClient` syncs `RoomManager` from `RoomListEvent`, requested on every session init and pushed on membership changes; `LobbyUI` renders whatever arrives, with a Play button for any `Spatial` room). Joins are **server-confirmed**: `WsClient.joinRoom()` only sends the request; membership, the spatial mode and the player set change on `JoinRoomResultEvent` (`roomJoined` / `roomJoinFailed` events). The lobby state returns to the *home room* (the room the server auto-joined on connect, `WsClient.homeRoomId`); the game state (re)joins the room whose Play was clicked. The only client-side room ids left are icon lookups in `LobbyUI`.
- **`clientId` ≠ `userId`.** `clientId` is per connection (new on every reconnect; avatars and room membership use it); `userId` is the stable identity (presence, chat authorship, "own" messages). Don't key anything that should outlive a reconnect by `clientId`. Message ids are global across rooms, not per room — gaps within a room are normal.
- **A user key is a device, not a user.** One user can have many keys (each logged-in device has its own), and a key can move to another user (a login reuses it). Never treat `key hash → user` as 1:1 in the other direction; `ClientSession.KeyHash` is the key *this connection* came in with.
- **Passwords cross the socket in clear.** `LoginRequest` / `ClaimAccountRequest` carry the password as typed (hashed only server-side), so production must be served over TLS (`wss:`); never log request bodies.
- **Avatars come from the game server, not the page origin.** In dev the page is `:5001` and the images are `:5000` — build the URL with `WsClient.avatarUrl()`, never a relative path.
- **The chat database is local state, not source.** Dev runs write `WsServer/WsServer/data/chat.db` (+ `-wal`/`-shm`; gitignored); in Docker it is the `game-data` volume at `/app/data` (the only path the non-root user can write). Deleting the files wipes history and users, and gives the history a new epoch.
- **MemoryPack `double` for times.** `SentAtMs` / `LastSeenMs` are `double` on the wire on purpose: a C# `long` becomes a TS `bigint` in the generated code.
- Keep `[MemoryPackable]` message types simple (flat, immutable-ish, no complex inheritance) — the serializer and TS generator both assume that.
