# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

WsCore is a real-time multiplayer game server: a .NET 10 / ASP.NET Core WebSocket backend and a TypeScript (Vite) client, joined by a shared MemoryPack binary protocol. The client is a **unified single-socket app**: one `WsClient` (one WebSocket) lives the whole session, and the Discord-style lobby (text chat) and the 3D Three.js scene are **UI states** of one shell, not separate apps. (Roadmap stage 2 replaced the old 2D-Phaser / 3D / lobby split; see `.plans/`.)

## Repository layout

- `WsServer/WsServer/` — the entire server (one project; older docs describe it as several). Notable folders:
  - `Shared/` — transport-agnostic infrastructure: `MessageSerializer`, `ReflectionServerLogicProvider`, `GameMessenger`, `ConnectionManager`, `Rooms/`, `StaticFileCaching`, and `Shared/Abstract/` interfaces.
  - `Sessions/` — `SessionManager` + `ClientSession`: per-connection identity (name, slots, chat rate limit) and every room transition, incl. spawning/removing the game avatar (see [Runtime architecture](#runtime-architecture)); `UserDirectory` + `UserAccount`: the stable users behind connections, presence (online / away / offline) and accounts (a user's keys, login + password hash, profile); `PasswordHasher` (PBKDF2); `AvatarImage` (upload validation + the `/avatars/{userId}` endpoint).
  - `Chat/` — `ChatHistoryService`: message ids, the per-room in-memory history window, history paging.
  - `Moderation/` — `ChannelPermissions` (who may do what in each channel: server admins, channel admins with rights + title, default member permissions, restrictions) and `ModerationService` (the rules for changing it, the chat-send check, message deletion).
  - `Push/` — Web Push for chat: `PushService` (subscriptions, who is notified, background delivery), `WebPushCrypto` (RFC 8291 aes128gcm encryption, `VapidKeys` — RFC 8292 JWT), `WebPushSender` (the HTTP POST; `IPushSender` is replaced in tests).
  - `Voice/` — `VoiceService`: voice channels (membership separate from the text room, the participant roster, WebRTC signalling relay, TURN credentials).
  - `Games/` — the games portal: `GameCatalog` (games, releases, each game's hidden room, drafts), `GameBuild` (unpacking an uploaded build) + `JamSdkInjector` (the bridge tag), `GamesHttp` (the games origin + the `/api/games…` REST API), `ApiTokens` (tokens an agent publishes with), `GameAnalytics` (play sessions, plays, views, game events), `Leaderboards` + `LeaderboardRequests` (boards in the jam / Yandex shape), `ImageInfo` (a picture's type and size from its header) + `GamePage` (a game page's link-preview tags), `AgentTools` (the MCP tools at `/agent/mcp`) + `UploadSessions` (their chunked uploads) + `Docs/*.md` (the agent's handbook, embedded), and `jam-sdk.js` — the jam portal's `window.Jam` bridge, vendored unchanged (embedded resource).
  - `Persistence/` — `IChatStorage` (`SqliteChatStorage` / `NullChatStorage`): durable chat history + known users behind one write-behind worker thread.
  - `Game/Core/` — game simulation (`GameModel`, `Player`, `Bullet`, `World/`).
  - `Game/Protocol/{Domain}/` — message contracts grouped by domain (`Chat`, `Map`, `Player`, `GameState`, `Bullets`, `Rooms`, `Connection`, `Presence`, `Account`, `Moderation`, `Push`, `Voice`, `Games`), each with `Requests/`, `Events/`, `Handlers/`.
- `tools/ascii-art/` — the chat's ASCII-art catalog: `art.txt` (the source: our own pictures, ids forever) and `build.mjs` (`node tools/ascii-art/build.mjs` normalizes and filters it — printable ASCII, ≤ 48 × 24 — into `WsCore.Client/src/lobby/asciiArt.json`, keeping ids gone from the source as `hidden`; the JSON is generated, prettier-ignored, committed).
- `WsServer/WsServer.TestClient/` — a RazorConsole console app that boots an **embedded** server + interactive terminal UI. Run with `dotnet run` for local testing without the browser client.
- `WsCore.Client/src/` — TS client (unified single-socket app):
  - `app/` — the shell: `ChatAlerts` (unread counter, page-shown notifications, the push subscription — see [Runtime architecture](#runtime-architecture)), `App` (owns the one `WsClient`, connects once, `lobby`↔`game` state machine, connection banner, reconnect re-init, keeps the stored identity in step with account events), `LobbyState` (drives `LobbyUI` and the profile dialog from client events; no own socket) and `IdentityStorage` (the user key + last name in `localStorage`).
  - `game/` — the Three.js scene (was `3d/`): `GameScene` (scene/camera/renderer/RAF/input + full `exit()` teardown), `Player` (pure state, implements `IPlayer`), `PlayerView` (the sprite/nick visual), `World`, `MapObject`.
  - `lobby/` — `LobbyUI` (rooms, chat (ASCII-art messages drawn as a `<pre>` whose font shrinks to the column — container units, never wraps), member list with avatars, @logins, role badges and user cards; links in messages open only after an "Открыть ссылку?" popover; adaptive: ≤ 1024px a narrower sidebar, ≤ 760px the sidebar is a drawer behind ☰, the room search folds into an icon, the user card is a bottom sheet, the lobby is sized to `visualViewport` so the keyboard never covers the composer), `ProfileDialog` (own profile: name, avatar, about, claim / log out), `ChannelDialog` (channel management: permissions, admins, restrictions, one member's page) + `ChatPicker` (the composer's ☺ popover: «Каомодзи» inserted at the caret, «ASCII-арт» sent at once by id; search, categories, «Недавние» in `localStorage`), `AsciiArt` (the bundled art catalog `asciiArt.json`: lookup by id, search, the `[арт: …]` text label; pure, unit-tested) + `kaomoji.ts` + CSS only (no app logic).
  - `network/` — `WsConnection` (transport: reconnect/backoff, silence watchdog, `connectionStatus`) → `WsClient` (session state: server-driven rooms, server-confirmed joins, players only while in a spatial room, the per-room chat cache and the presence roster; a typed `on()`/`emit()` event emitter), `ChatLog` (the chat cache: pure, unit-tested), `Permissions` (`PermissionStore`: the client mirror of channel roles — pure, unit-tested), `rooms/`, and `network/protocol/` (**generated** — see below).
  - `portal/` — the games portal: `PortalUI` (catalog + a game's page, drawn in the lobby's main area), `MediaGallery` (a game page's pictures: a large picture with ‹ › + counter and a row of thumbnails — the cover, then the screenshots — paging round by arrows / keys / swipe; a click opens them full screen; the state survives page re-draws; its helpers pure, unit-tested), `GameHost` (the stage: the game's sandboxed iframe on the games origin, loading screen, mock ad card), `JamBridge` (the host half of the jam SDK's postMessage protocol; pure, unit-tested), `PlaySession` (attention timer → heartbeats + buffered game events; pure, unit-tested), `GameEditor` (the card editor: fields, published, cover / header / screenshots) + `GamesApi` (its REST client, `X-User-Key`; unit-tested), `StatsView` (the analytics panels: a game's, the portal's) + `Charts` (SVG line / column / ranked-bar charts with hover and keyboard) + `Stats` (the stats shape, every day of the period, ticks, Russian number / duration formats; pure, unit-tested), `Leaderboard` (avatar paths → absolute, the SDK proxy's arguments, the panel payload, an unnamed visitor's pending scores; pure, unit-tested), `Markdown` (the descriptions' little Markdown as DOM nodes; pure, unit-tested), `Portal.css` (loaded with the lobby's CSS).
  - `voice/` — `VoiceChat`: the WebRTC mesh (microphone, one `RTCPeerConnection` per participant, signalling through `WsClient`, mute / deafen, the speaking indicator, rejoin after a reconnect). Owned by `App` (outlives lobby ↔ game); browser APIs injected (`VoiceDeps`) so it is unit-tested with fakes.
  - `utils/` — `Recents` (a most-recent-first list in `localStorage`), `UnreadBadge` (the unread count in the tab title, on the favicon and via `navigator.setAppBadge`), `Emitter`, `Keyboard`, `ChatUI`, `Common`, `SnapshotInterpolation` (tick-snapshot interpolation buffer + server clock), `IdleDetector` (away/afk detection), `AvatarImage` (downsizes a picked picture to the 128×128 JPEG that is uploaded), `Linkify` (splits a message into text and http(s) links — the same link shapes the server's `SendLinks` check recognises; pure, unit-tested), `UpdateChecker` (notices a newer deployed build: compares the build id compiled into the page — `__APP_BUILD__`, set in `vite.config.ts` next to `__APP_VERSION__` from `package.json` — with `/version.json`, which the build writes to `dist/`; polls every 5 min, when the tab is shown again and after a reconnect; owned by `App`, off in dev; the lobby brand row shows `v{version}` and, once an update is seen, the «Обновить» button that reloads the page; pure, unit-tested).
  - `public/` (served as-is, not bundled): `sw.js` — the service worker (installability + showing pushes + notification clicks), `manifest.webmanifest` + `icons/` (192/512, maskable, apple-touch, the monochrome Android `badge-96`). Both `sw.js` and the manifest are served `no-cache`.
  - `main.ts` registers `/sw.js` and is a thin entry that builds `App` from the entry form (`#name-form` in `index.html`: quick entry by name, or — via "I have an account" — login + password). **A returning visitor skips the form**: if `localStorage` holds a user key (`wscore.userKey`), the app enters straight away as that user (an inline script in `index.html` hides the form before the module loads, so it does not flash); a claimed account identifies with an empty name so the server's name wins over a stale stored one (`wscore.login` marks it). The form shows only on the first visit, after a logout, or for `/#login` (a guest's "У меня уже есть аккаунт" in the profile; the hash is one-shot).
  - `*.test.ts` files sit next to the code they cover (e.g. `network/rooms/RoomManager.test.ts`, `network/protocol/protocol.test.ts`) — see [Testing](#testing).
- `WsServer/WsServer.Tests/` — xUnit project: unit tests for `GameModel`/`RoomManager`/`MessageSerializer`, plus a real-WebSocket integration test in `Integration/` (see [Testing](#testing)).
- `AGENTS.md` (root) and `WsServer/AGENTS.md` — detailed prior guidance on conventions and the room system. Read them for depth; note both predate the single-project merge (see Gotchas).

## Commands

For interactive development, run server and client in **separate terminals**. For **automated testing**, bring the whole stack up in the background with `scripts/dev-up.sh` and drive the browser via the integrated-browser MCP — see [Testing](#testing).

```bash
# Server (http://localhost:5000, WebSocket at /ws, dashboard JSON at /info — connections,
# gamePlayers (avatars incl. the 10 built-in bots), per-room user counts)
cd WsServer/WsServer && dotnet run

# Client (Vite dev server at http://localhost:5001)
cd WsCore.Client && npm install && npm start

# Format TS after changes (required; enforced style)
cd WsCore.Client && npm run format        # or: npm run format:check

# Client production bundle (dist/: index.html + hashed chunks; three.js is a lazy chunk loaded on Play)
cd WsCore.Client && npm run build

# Embedded test client (server + terminal UI in one process)
cd WsServer/WsServer.TestClient && dotnet run

# --- automated testing helpers ---
scripts/dev-up.sh                  # start server + client in background (logs/pids in .run/)
CLIENT_PORT=5199 scripts/dev-up.sh # ...on an alt client port (dodge a stale :5001 service worker)
scripts/dev-down.sh                # stop both (reads the client port from .run/client.port)
```

The client is one app: it opens in the lobby; the **Play** button on a spatial room enters the 3D scene (the `game` room is currently **hidden from room lists**, so the lobby offers no Play button — the scene is reachable only by joining `game` by id, as tests / LoadTest / TestClient do), **Back to Lobby** returns, and the single WebSocket persists across those switches and across server restarts (auto-reconnect). In dev the client hard-codes the server to port 5000; in production it uses the current origin.

Then, using the browser MCP tools (prefer `browser_eval` for assertions, `browser_console` for errors, `browser_screenshot` only when a visual matters):

1. `browser_navigate` → `http://localhost:5001`; click **Enter Lobby** (`#name-text-input` + the form button). Assert the lobby renders (`#lobby-container`) and `browser_console` is error-free.
2. *(Steps 2–4 need the `game` room in the list — it is hidden now; to run them, drop `isHidden: true` in `GameServer.InitializeDefaultRooms` locally.)* Click **Play** on the `game` room → assert the 3D canvas exists: `document.querySelectorAll('#game canvas').length === 1`.
3. Click **Back to Lobby** → assert `document.querySelectorAll('#game canvas').length === 0`.
4. **Leak check — repeat lobby→game→lobby ~10×**, then assert *nothing accumulates*:
   - `#game canvas` ≤ 1, `#chat-overlay` ≤ 1, `#lobby-container` ≤ 1
   - back buttons: `[...document.querySelectorAll('div')].filter(d => d.textContent === 'Back to Lobby').length` ≤ 1

5. **Reconnect** — assert the banner (`#connection-banner`) shows during an outage and hides on recovery. Two ways to exercise it:
   - **Server-down-first (reliable in the integrated browser):** stop the server (`scripts/dev-down.sh server`), *then* load the app and enter the lobby → the banner reads `Connection lost — reconnecting…` while the backoff loop retries. Start the server (`scripts/dev-up.sh`) → the banner hides, the name form stays hidden, and the lobby repopulates (reconnect assigns a *new* clientId — session restoration is a later roadmap milestone).
   - Kill-while-connected also triggers the banner in a real browser, but **the VS Code integrated browser reloads the tab when an established WebSocket is killed** (the app itself only calls `location.reload` after a logout), which masks the banner — prefer the server-down-first method there.

6. **Chat history + presence** (two browser contexts = two users; a fresh context is a new user, the user key lives in `localStorage`): messages survive a page reload and a server restart (start the server with `GameServer__ChatDatabasePath` pointing at a scratch file, and `GameServer__ChatCooldownSeconds=0` to post in bulk); entering a room renders exactly one page (`.lobby-message-text` count = 50) at the bottom; setting `.lobby-messages` `scrollTop = 0` prepends the previous page **without moving** the message under the viewport (compare its `getBoundingClientRect().top` before/after) until `.lobby-history-status` reads `Начало истории`; a message arriving while scrolled up shows `.lobby-new-messages` instead of jumping; a user who leaves stays in `.lobby-user-item` as `.lobby-user-offline`; five idle minutes (`page.clock.fastForward('05:05')` in Playwright) turn them `.lobby-user-away`, input brings them back. This has been run and passes (19 checks).

## Message protocol (the core abstraction)

Every client↔server message is framed as `[TypeId: 1 byte][MemoryPack payload]`.

- A message is a `[MemoryPackable] partial class` implementing **`IClientRequest`** (client→server) or **`IServerEvent`** (server→client), with a `static byte TypeId`. `[GenerateTypeScript]` opts it into TS codegen.
- `ReflectionServerLogicProvider` scans the assembly at startup, registering every `IClientRequest`/`IServerEvent` by its `TypeId` and wiring each request to its handler. **TypeIds must be unique** — a collision throws `DuplicateMessageIdException` at boot (a stale hand-maintained `ServerMessageType.cs` map used to promise this but had drifted out of sync with real ids and was removed; before picking a new id, grep for `TypeId =>` across `Game/Protocol/**` to see what's taken).
- Request handlers subclass `RequestHandlerBase<TRequest>` and are constructed via DI (`ClientRequestHandlerFactory`), so they can inject `IGameMessenger`, `ILogger`, etc.
- `WebSocketHandler` also accepts **JSON text frames** as a debugging fallback (it reflects fields onto the request type by name); the real client always sends binary.

### Adding a new message type

1. Create the class under the right `Game/Protocol/{Domain}/{Requests|Events}/`, mark it `[MemoryPackable]` (+ `[GenerateTypeScript]`), implement `IClientRequest`/`IServerEvent`, assign an unused `TypeId`.
2. For a request, add a `{Name}Handler : RequestHandlerBase<{Name}Request>` in that domain's `Handlers/`. Discovery is automatic — no manual registration.
3. Regenerate client TS types (below), then handle the message in the client's `WsClient`/`WsConnection` layer.

### Regenerating client TypeScript types — non-obvious

The generated files in `WsCore.Client/src/network/protocol/` (readers/writers + model classes) come from MemoryPack's TS source generator, but the generator output is **commented out** in `WsServer/WsServer/WsServer.csproj` (the `MemoryPackGenerator_TypeScriptOutputDirectory` block). The checked-in TS is the source of truth day-to-day. To regenerate after changing a `[GenerateTypeScript]` type, **uncomment that block, build the server, then re-comment it**, and run `npm run format`.

## Runtime architecture

- **A connection is not a player.** Connecting creates a `ClientSession` (name, equipment slots, chat cooldown — `Sessions/SessionManager.cs`) and puts the client in the `lobby` room; a `Player` avatar in `GameModel` (id == clientId) exists only while the client is in a room supporting `RoomCompatibility.Spatial` (the `game` room) and is removed when it leaves that room or disconnects. All room transitions go through `SessionManager.JoinRoom`, which answers the joiner with `JoinRoomResultEvent` (success or failure, before any room state). Scoping: entering the game → the joiner gets `GameStateUpdateEvent`, other spatial members `PlayerJoinedEvent`; leaving/disconnect → `PlayerLeftEvent` to spatial members; shots/slots/respawns/map changes → spatial members (`IGameMessenger.BroadcastToSpatial`); chat → the sender's room only (`BroadcastToRoom`); chat history → the requester; presence → every identified connection (`BroadcastWhere`); `SetPlayerNameEvent` → the client's room (for a client with an avatar: the spatial audience); `RoomUsersUpdateEvent` → the room's members; `RoomListEvent` → pushed to non-spatial clients on any membership change; `VoiceRosterEvent` → every identified connection that may see the voice channel; `VoiceSignalEvent` → one participant of the sender's voice channel. Game requests (move/target/shoot/respawn/slots/map) from a client without an avatar are no-ops (slots are remembered on the session and applied at spawn).
- **Users and presence.** Client ids change on every (re)connect, so a client that wants a stable identity sends `IdentifyRequest { UserKey, Name }` as its first request (`WsClient` does, with a random key from `localStorage` — `wscore.userKey`; it also sets the name, replacing the old `SetPlayerNameRequest` on init). `SessionManager.Identify` binds the session to a `UserAccount` (`UserDirectory`: key → user, keyed by the key's SHA-256 — the key itself is a bearer secret and is never stored or broadcast; others only see the public `UserId`). A user may have several sessions (reconnect overlap, a second tab). Presence = `Offline` (no sessions) / `Online` (any session active) / `Away` (all sessions idle), plus the room of an active session. **Users are never removed from the member list when they disconnect — they turn offline** (with `LastSeenMs`). The identifying client gets `PresenceSnapshotEvent` (its `UserId`, everyone online, the `PresenceMaxOfflineUsers` most recently seen offline users); after that every identified connection — in any room, lobby or game — gets a `PresenceUpdateEvent` when a user's status / room / name changes (`PublishPresence` diffs against what was last announced). Away is client-driven (`IdleDetector`: 5 min without input → `SetAwayRequest`), so its announcements are rate-limited: the state is applied at once but flushed at most every `PresenceFlushIntervalSeconds` (`SessionManager.FlushPresence`, called each tick). Connections that never identify (LoadTest bots, the TestClient, old clients) stay anonymous: no presence traffic, `UserId` 0 in chat and in `RoomUserInfo`; the lobby lists them as guests while they are in the room (once they have a name).
- **Accounts and profiles.** A user starts as a **guest**: it exists only through the key in one browser. `ClaimAccountRequest { Login, Password }` *claims* it — the same user (id, history, name) gets a login (3–32 of `a-z 0-9 . _ -`, case-insensitive, unique) and a password (≥ 8 chars; PBKDF2-SHA512, `PasswordHashIterations`). `LoginRequest { Login, Password, UserKey }` enters a claimed account from another device: `UserKey` is a fresh key the client made up, which on success becomes one more key of the account (`UserDirectory.BindKey`; a user has any number of keys, one per device) — so every later connect is a plain `IdentifyRequest` with it, and the password is never stored client-side. The client sends it *instead of* identifying (`WsClient.loginOnConnect`); a connection that had identified as a guest leaves that user. `LogoutRequest` unbinds this connection's key (other devices stay logged in; a guest cannot log out — its key is the only way back). Each is answered to the requester with `AccountResultEvent { Action, Success, Error, Login }` (`Error` is an `AccountError` code the client words itself); `PresenceSnapshotEvent.YourLogin` tells an identifying client whether its user is claimed. **Hashing never runs on the tick thread**: `SessionManager` validates on the tick, hashes / verifies on the thread pool and applies the outcome on a later tick (`DeliverCompleted`); one such operation per session at a time (`ClientSession.AuthPending`). Abuse limits: every account/profile request is rate-limited per connection (`AccountRequestCooldownSeconds`), and `LoginMaxFailures` wrong passwords in a row lock that login for `LoginLockoutSeconds` (devices already logged in are unaffected — they use their key). The **profile** — "about" (`UpdateProfileRequest`, `MaxAboutLength` 190) and the avatar — belongs to any identified user, guest or claimed, and travels in `PresenceUserInfo` (`About`, `AvatarVersion`), so it reaches everyone through the usual presence updates. The avatar is uploaded over the socket (`SetAvatarRequest { Image }`: PNG / JPEG / WebP recognised by signature, ≤ `MaxAvatarBytes`; the client sends a 128×128 JPEG; empty = remove), stored as a blob and served by `GET /avatars/{userId}?v={AvatarVersion}` — `immutable` because the version (time-based, never reused) is part of the URL, `nosniff`, content type from the signature. An `IdentifyRequest` with an empty name keeps the user's stored name. A rename on one connection renames every connection of the same user (otherwise another device would keep showing — and chatting under — the old name). Rendered chat messages re-resolve their author's avatar, @login, role and delete button on every presence / permissions change (`LobbyUI.refreshMessages`), since history can arrive before the member list and all of these change. The login of a claimed account is public (`PresenceUserInfo.Login`, shown as `@login`).
- **Roles and permissions** (Telegram-style, per channel = room; `Moderation/`). A **server admin** (`UserAccount.IsAdmin`, `PresenceUserInfo.IsAdmin`) has every right in every channel; logins in `GameServer:AdminLogins` (`appsettings.json`: `gritsenko`) are server admins by configuration (granted at startup and on claim, cannot be demoted); others are appointed by a server admin (`SetServerAdminRequest`). A **channel admin** has `ChannelRights` flags — `DeleteMessages`, `RestrictMembers` (mute / ban + the channel's defaults), `AddAdmins`, `InviteUsers` (access to a private channel) — and an optional title (`SetChannelAdminRequest`; rights 0 = demote). Everyone else has the channel's default `MemberPermissions` (`SendMessages`, `SendLinks`; `SetChannelDefaultsRequest`) minus their **restriction** (`SetChannelRestrictionRequest { Denied, Banned, DurationSeconds }`, 0 = forever; expiry is checked on use). Rules (`ModerationService`): admin roles need a claimed account; one grants only rights one has and cannot change an admin who has rights one lacks; nobody changes their own role (a server admin may set their own title); admins cannot be restricted; the home room (`lobby`) can mute but not ban. A ban moves the member's connections in that room back to the home room and `SessionManager.JoinRoom` refuses them (`JoinRoomResultEvent.Error = "banned"`; the game scene leaves when the server moves it out). The chat handler refuses muted / banned / link-carrying messages (`ModerationService.CheckCanSend`; a deliberately simple link regex). `DeleteChatMessageRequest`: own messages (while in the in-memory window) or anyone's with `DeleteMessages`; removed from the window and the database, and `ChatMessageDeletedEvent` goes to **every** connection (anyone may have the room cached). State reaches clients as `ChannelPermissionsEvent` (every channel the user may see with `Reset` after the identify, then the changed channel to every identified connection that may see it); every request is answered with `ModerationResultEvent { Action, Success, Error }` (also used to tell a sender why a message was refused), rate-limited by `ModerationRequestCooldownSeconds`. Stored in `users.is_admin`, `channels` and `channel_members` (schema v2). A restricted *guest* can shed the restriction with a fresh browser key — restrictions are a speed bump, not identity-proof.
- **Channels = rooms; created and private channels.** Besides the built-in rooms a **server admin** creates channels (`CreateChannelRequest { Name, IsPrivate }` → `ModerationResultEvent.RoomId` = the new id, `c` + 10 random base-36 chars; the lobby then joins it), renames them / makes them private or public (`UpdateChannelRequest`) and deletes them (`DeleteChannelRequest`: everyone inside goes to the home room, the room, its permissions and its whole history are dropped). Built-in rooms cannot be changed (`built_in`). Created channels are plain text-chat rooms, stored as `channels` rows with a `name` (schema v4: `channels.name / is_private / created_ms`, `channel_members.has_access`) and recreated at startup (`ChannelPermissions.CreatedChannels` → `GameServer.CreateChannelRoom`). A **private** channel is seen only by server admins, its channel admins and the members given access (`SetChannelAccessRequest { RoomId, UserId, HasAccess }`, needs `InviteUsers`; guests may be given access) — `ChannelPermissions.CanSee` gates the room list (`SessionManager.BuildRoomList(clientId)`; `BroadcastRoomList` sends the shared public list once and a personal one to whoever sees a private channel), `JoinRoom` (`no_access`), `ChannelPermissionsEvent` and push. Whoever loses sight of a channel (access taken, demoted, channel made private, logout) is moved to the home room (`SessionManager.RefreshVisibility` / `EvictUnauthorized`). Presence never names a private channel as a user's room (`RoomId` = null). `MaxChannelNameLength` (32), `MaxCreatedChannels` (100). Client: the "+" next to "Каналы" (server admins) opens `CreateChannelDialog`; private channels show a lock; `ChannelDialog` has the tabs **Доступ** (private channels) and **Канал** (name / private / delete with an inline second click, created channels, server admins), and an access section on a member's page.
- **Voice channels** (`Voice/VoiceService.cs`, `voice/VoiceChat.ts`; Discord-style). A voice channel is a room supporting `VoiceChat` (the built-in `voice`, or a created channel with `CreateChannelRequest.IsVoice` — `channels.is_voice`, schema v5); it also has its text chat. **Voice membership is separate from the text room**: a connection is in one text room and, independently, in at most one voice channel, so a user reads any channel while talking (clicking a voice channel in the lobby joins its text *and* its voice). Audio is a **WebRTC mesh** (peer to peer; the server never sees media): `VoiceJoinRequest` → `VoiceJoinResultEvent { Peers, IceServers }` — the joiner offers to every client already there, they answer, so offers never cross; the joiner is also the side that restarts ICE. `VoiceSignalRequest { TargetClientId, Kind (offer / answer / candidate), Data }` is relayed as `VoiceSignalEvent` only between participants of the same channel (≤ `VoiceMaxSignalBytes`, token bucket `VoiceSignalBurst` / `VoiceSignalsPerSecond`). `VoiceRosterEvent` (who is in which channel, with mute / deafen; a `Reset` after every identify / visibility change, then per channel) goes to every identified connection that may see the channel — the client's roster is the truth for its mesh (a peer gone from it is hung up). Rules: identified users only; visible + not banned; `VoiceMaxParticipants` (8); one voice connection per user (another tab joining takes over: `VoiceLeftEvent { Reason = moved }`); ban / lost access / logout / channel deleted take a participant out (`removed`) — `VoiceService` follows `SessionManager.VisibilityChanged` / `ChannelChanged`; a disconnect just drops the participant. ICE servers: `VoiceStunUrls` + (with `VoiceTurnSecret`) `VoiceTurnUrls` with TURN REST credentials (`expiry:userId`, base64 HMAC-SHA1) — coturn `use-auth-secret`. Client: the microphone opens on join (a click) and is released on leave; **device choice** («Настройки голоса» — the gear in the voice panel, or «Микрофон и динамики» in the profile; `lobby/VoiceSettingsDialog`): the microphone (`VoiceChat.setInputDevice` — in a call a new `getUserMedia({ deviceId: exact })` track goes to every peer by `RTCRtpSender.replaceTrack`, no renegotiation; a device that cannot be opened keeps the old one) and the output (`setOutputDevice` → `HTMLMediaElement.setSinkId` on every peer's `<audio>`, not offered where the browser lacks it — Safari), both kept in `localStorage` (`wscore.voiceInput` / `wscore.voiceOutput`; the next join asks for the remembered mic as `ideal`, so an unplugged one falls back); until the microphone was allowed once the browser hides device names — «Разрешить» asks for it; «Проверить звук» plays a chime on the chosen output; mute = `track.enabled = false`, deafen mutes the `<audio>` elements and the mic; the speaking ring is an `AnalyserNode` RMS level per stream; after a reconnect `VoiceChat` rejoins once the new connection identified (`identified` event). UI: participants under the channel, the voice panel above the profile (mic / sound / hang up), compact mic + hang-up in the chat header on phones.
- **New-message alerts and Web Push** (`app/ChatAlerts.ts`, `Push/PushService.cs`). The page counts messages from others that arrive while it is not looked at (hidden tab or unfocused window) — tab title `(N) …`, a red counter drawn on the favicon, the installed app's icon badge — and clears the count (and its notifications) when looked at again. Notifications come from **exactly one source**: while the page is open and its user active, the page shows them itself (`registration.showNotification`); while the user is **away or offline** (`UserAccount.Status != Online`) the server pushes instead — it never pushes to an online user. A room has one notification (tag `chat-{roomId}`) that counts up, in the page and in `sw.js` alike. Subscribing: the profile's "Включить уведомления" asks for the permission (a click), subscribes `PushManager` with the server's VAPID key and sends `PushSubscribeRequest { Endpoint, P256dh, Auth }`; the key arrives as `PushConfigEvent` after **every** identify, and the client re-sends its subscription then (idempotent; it also re-binds the device to the user it now is; a subscription made with another key is replaced). A subscription belongs to a user and the device key it came with: `LogoutRequest` drops it, a push service answering 404/410 drops it, `PushUnsubscribeRequest` / turning it off drops it. Rules: not to the author, not to a user banned from the room, at most one push per user and room per `PushMinIntervalSeconds`, at most `PushMaxSubscriptionsPerUser` devices. Delivery never touches the tick thread: encryption + HTTP on four background workers fed by a bounded channel (overflow drops notifications). VAPID keys: `PushVapidPublicKey`/`PrivateKey` if configured, else generated once and kept in the database's `meta` table (changing them invalidates every subscription); `PushSubject` must be a real `https:`/`mailto:` (Apple rejects localhost). `PushEnabled=false` turns it all off. iOS: push only works in a web app added to the Home Screen — the profile says so (`AlertsStatus 'install'`). The payload is JSON read by `sw.js` (`type`, `roomId`, `roomName`, `author`, `avatar` path, `body` ≤ 200 chars, `sentAtMs`); a notification click focuses an open window and posts `open-room` (the lobby switches room) or opens `/`.
- **Games portal** (`Games/`, `portal/`; plan in `.plans/2026-11-24-games-portal-plan.md`). A catalog of HTML5 games, compatible with the MY.GAMES JAM portal (`~/projects/rnd/jam.my.games`): a game written against its `window.Jam` SDK runs unchanged. **Builds are served from another origin** (`GamesOrigin`, prod `https://play.tox.gritsenko.biz`, dev `:5002`; same process, routed by Host in `UseGamesOrigin`, first in the pipeline): the user key lives in this origin's `localStorage`, so a game's JS must never run here. A game = `GameCatalog` entry + a hidden text room `g-{id}` (not in room lists; joined by id; while a draft `ChannelPermissions.SetOwnerOnly` makes it private to its owner + server admins, and unpublishing evicts); playing = being in that room (`LobbyState` starts `GameHost` on the confirmed join and keeps it across a reconnect — `rejoiningGame`; the client's `RoomManager.syncRooms` keeps the hidden joined room). `GameCatalogEvent` (public + own drafts) goes on connect, after every identify and on any change. **Publishing is server admins only**, through REST with an API token (`Authorization: Bearer tox_…`, made in the profile — `CreateApiTokenRequest`; hash stored; idle 60 days → dead): `POST /api/games`, `PATCH /api/games/{id}`, `POST …/visibility`, `PUT …/build?filename=&version=&notes=` (body = the .zip / .html; reserved release number → unpacked off the tick thread into `r{no}.tmp-…` → renamed → committed; refused builds leave nothing; old releases beyond `GameKeepReleases` deleted from disk, records kept), `GET /api/games` (public), `GET /api/me`. Stored in `games`, `game_releases`, `api_tokens` (schema v6); builds on disk under `GamesDataPath`. `/games` and `/games/{slug}` load the app shell (`MapFallbackToFile`) and open **without the entry form** (anonymous connection: browse and play; «Гость» → the form to chat). **Analytics** (`GameAnalytics`, `portal/PlaySession.ts`; the jam portal's model): the page times **attention** (1 s tick, only while visible + focused + no mock ad; gaps > 3 s not credited) and reports `GamePlayBeatRequest` — first beat = a launch, then every 20 s of played time, on hide and `Ended` on leaving; the server clamps it (monotonic, ≤ wall time since the session started + 5 s, ≤ `GamePlayMaxSessionHours`). Anonymous visitors are told apart by `wscore.visitorId` (random, only sent while unidentified; no IP / user agent stored — just `mobile` / `desktop`). Stored (schema v7): `games.*_total` (never touched by game edits — the upsert leaves them), `game_play_sessions`, `game_play_events`, `game_hits` (raw: `GameAnalyticsRetentionDays` 180), `game_daily` (per game + `''` for the whole portal; forever). `GET /api/games/{id}/stats?days=N` (owner / admins) and `GET /api/games/stats` (admins): totals, sessions (median, longest, ≥ 1/3/10 min), players, returning players (≥ 2 days), daily rows, events, levels, view sources. **Leaderboards** (`Leaderboards`, the jam's `leaderboards.py`): a board (`[a-z0-9_]{1,64}`, ≤ 12 per game) is created by its first score; one row per board × user holds the best (+ its `extraData` ≤ 1024, `submissions`); ranks on read — better score first, then whoever got there earlier; `|score| ≤ 10^15`, floored. **Identified users only write** (an unnamed visitor gets `{ ok: false, reason: 'not_signed_in' }` — the page keeps its best and lowest in `sessionStorage` `wscore.pendingScores` and sends them after the visitor enters by name, showing «Войдите, чтобы попасть в таблицу рекордов» in the stage); `LeaderboardWriteCooldownSeconds` per user × board (`too_fast`). The authors' (owner, admins) rows are kept and flagged `own`. `UserAccount.LeaderboardHidden` (profile «Скрыть меня из таблиц рекордов», `SetLeaderboardHiddenRequest`, `PresenceSnapshotEvent.YourLeaderboardHidden`) is a display rule: others never see the row, ranks close up, the player sees it with `hiddenFromOthers`. Everything is in memory (tick thread; written behind: `leaderboards`, `leaderboard_entries`, `users.leaderboard_hidden` — schema v8). Over the socket: `LeaderboardRequest { RequestId, GameId, Board, Op: score / entries / player / description / boards }` → `LeaderboardResultEvent { RequestId, Ok, Status, ResultJson }` — the JSON is the jam / Yandex shape built on the server, avatar URLs as paths that the page makes absolute (`absolutizeAvatars`) before the bridge hands them to the game; `WsClient.leaderboard()` is a promise with the SDK's 8 s timeout. Board settings (title, lower-is-better, numeric with 0–2 decimals or time) / reset / delete: `LeaderboardConfigRequest` (owner, admins; the game page's `.portal-board-settings`) or REST `PATCH|DELETE /api/games/{id}/leaderboards/{name}`, `POST …/reset`; `GET /api/games/{id}/leaderboards` = the page's panel. Any change → `LeaderboardChangedEvent` to the game's room; a **new leader** (not an author, not hidden) → a chat line in the game's room from «Таблица рекордов». **The card's pictures and link previews** (schema v9 `game_media`; files under `{GamesDataPath}/{gameId}/media/{id}.{ext}`, served from the main origin at `/game-media/{gameId}/{id}.{ext}` — `immutable`, `nosniff`, type by signature): one **cover** (cards, the page, `og:image`) and one **header** (a 4:1 strip atop the page) — a new one replaces the old and its file is deleted — and up to `MaxGameScreenshots` (12) **screenshots**, ordered as a whole list (`PUT /api/games/{id}/screenshots { ids }`, ids left out are removed — the jam's `attach_media`). Upload: `PUT /api/games/{id}/media?kind=cover|header|screenshot` with the picture as the body (≤ `GameMaxMediaMb`; PNG / JPEG / WebP / GIF, width × height read from the header by `ImageInfo` — no image library on the server); `DELETE /api/games/{id}/media/{mediaId}`. The browser editor (`GameEditor`, «Редактировать» on the page for the owner and admins) scales pictures down first (`utils/PictureScale`: cover ≤ 1200, header ≤ 2400×600, screenshots ≤ 1920; JPEG) and calls the same REST API **as the browser's user: `X-User-Key`** (the socket's 64 KB messages cannot carry pictures) — so `/api` has a CORS policy for `PortalOrigins` (dev: the page is :5001). `GameInfo` carries `CoverUrl` / `HeaderUrl` / `Screenshots` as paths; `WsClient` makes them absolute. **Link previews:** `GET /games/{slug}` (`MapGamePages`, before the shell fallback) answers the built `index.html` with the game's `<title>`, description (the tagline), canonical, `og:title/description/url/image(+width/height/alt)`, `twitter:*` and `summary_large_image` only with a cover — for a **public** game; a draft or an unknown slug gets the page untouched. **The agent** (`AgentTools`, `/agent/mcp`, `ModelContextProtocol.AspNetCore`, stateless Streamable HTTP): the MY.GAMES JAM portal's tools by name, arguments and answer shape (`whoami`, `list_scopes` = `personal` only, `list_projects`, `get_project`, `create_project`, `update_project`, `set_visibility`, `push_build`, `upload_status`, `complete_build`, `update_release`, `push_media`, `attach_media`, `docs`), so an agent that publishes to the jam publishes here by changing the address. Auth = a personal token (`UseAgentAuth` answers 401 + `WWW-Authenticate: Bearer` before the transport); the profile shows the ready `claude mcp add --transport http --scope user tox …/agent/mcp --header "Authorization: Bearer tox_…"` once. Uploads (`UploadSessions`, in memory, 1 h): a tool opens a session and answers with `curl -f -T` commands to `PUT /agent/upload/{session}/{index}?t={ticket}` (the ticket is the authority; chunk length must be exact; `AgentUploadChunkMb` 0 = one chunk), `upload_status` lists `missing`, `complete_build` / `attach_media` assemble and run the **same code as REST** (`GamesHttp.PublishBuildAsync` / `AddPictureAsync`). Tool refusals are `McpException`s (the message reaches the agent); tool JSON keeps Cyrillic unescaped. OAuth sign-in (as the jam has) is not done — tokens only. **Analytics screens** (`StatsView` over `GET /api/games/{id}/stats` / `/api/games/stats`, fetched with `X-User-Key`): «Аналитика» on a game's page (its owner, admins) and «Статистика раздела» on the catalog (admins) — a period row (7 / 30 / 90 days) scoping everything below; stat tiles; «По дням» (views / launches / plays — one axis, a legend, crosshair + one tooltip), «Игроки по дням» (portal), «Время в игре по дням, минут» (columns); levels funnel, the game's events, view sources (ranked bars); the portal's table of games for the period (`StatsDto.Games`, from `game_daily` + distinct players from the sessions); a table view of every day. Colours: categorical slots 1–3 of the dataviz reference palette, dark steps, validated on the surface (`--series-1..3` on `#lobby-container`); text never in series colours; a reload dims the previous render instead of a skeleton.
- **ASCII art and kaomoji in chat.** Kaomoji are plain text (the picker inserts them into the composer). An **ASCII art travels like a sticker**: `ChatMessageRequest.ArtId` (the text is ignored then) → `ChatMessageEvent.ArtId` / `ChatMessageData.ArtId` / `messages.art_id` (schema v10); the server checks only the id's shape (`[a-z0-9-]{1,40}`, else dropped) and `ChatArtCooldownSeconds` (2 s, on top of the chat cooldown), never the catalog — the pictures are bundled with the client (`lobby/asciiArt.json`), so a message's height is known when it is drawn (the history's scroll correction depends on that) and an id this page does not know is drawn as «Арт недоступен». Catalog ids are never removed or reused (an art taken out of the picker stays, `hidden`). Push / page notifications and the in-game overlay show it as `[арт: title]` (the push says «ASCII-арт» — the server has no titles). Why not multi-line text: `InputSanitizer` strips newlines, `MaxChatLength` is 256 and the composer is one line — loosening that would let any client post walls of text.
- **Chat history.** Every chat message gets a global, strictly increasing `Id`, a timestamp and its author (`UserId`, name snapshot) in `ChatHistoryService.Append`, which caches it, queues it for the database and returns the `ChatMessageEvent` to broadcast — the live event and the stored message share the id, which is what lets clients merge the two. History is **pulled** by the client for its current room (`ChatHistoryRequest` → `ChatHistoryEvent`): `AfterId` = catch-up (everything after what the client has; a *reset* with the latest page if nothing is cached, the gap exceeds one page, or the `Epoch` differs), `BeforeId` = the page before the oldest message it has (scroll-up). `ChatHistoryPageSize` (50) per page. **Hot path = memory:** the newest `ChatHistoryCacheSize` (200) messages per room live in the service, so joins, reconnect catch-ups and the first scroll-back pages never touch the database; only a `BeforeId` older than that window queries storage — asynchronously on the storage thread, one query per session at a time (`ClientSession.HistoryQueryPending`), the answer delivered on a later tick via `ChatHistoryService.DeliverCompleted`. `Epoch` names the id space: stored in the database (stable across restarts), random per process without persistence — a client seeing a new epoch drops its cached ids.
- **Storage** (`Persistence/SqliteChatStorage`, enabled by `GameServer:ChatDatabasePath`; empty → `NullChatStorage`, nothing persists — the default for tests / LoadTest; a database that cannot be opened logs an error and falls back to it rather than stopping the server). One SQLite connection owned by one background thread fed by a bounded FIFO: the tick thread never does I/O; writes are write-behind and group-committed (everything queued = one transaction; WAL, `synchronous=NORMAL`); a query is ordered behind the appends queued before it, so it always sees them. Paging is keyset (`WHERE room_id = ? AND id < ? ORDER BY id DESC LIMIT ?` on the `(room_id, id)` index — no OFFSET). Users are three tables — `users` (name, last seen, login, password hash, about, avatar version), `user_keys` (key hash → user) and `avatars` (blob) — versioned by `PRAGMA user_version` (a pre-accounts database is migrated on open; v3 added `push_subscriptions`, v4 created channels); avatar reads go through the same queue (`LoadAvatar`, callable from the HTTP thread, bounded by a semaphore so the endpoint cannot crowd out chat writes). Retention: `ChatHistoryMaxMessagesPerRoom` and `UserRetentionDays`, applied at startup and hourly; `MaxKnownUsers` evicts the longest-offline user — both only ever drop **guests**, never a claimed account. Everything is read once at startup (`StorageSnapshot` → history windows + user directory); graceful shutdown stamps last-seen for connected users and flushes the queue (`Dispose`).
- **Client chat cache** (`network/ChatLog.ts`, owned by `WsClient`, one contiguous log per room): kept for the whole page session — across room switches, lobby↔game and reconnects. On every confirmed join `WsClient` sends a catch-up from the room's last cached id, so returning to a room renders instantly from the cache and fetches only what was missed; `loadOlderChat()` extends it backwards (one request at a time, with a timeout so a lost request can be retried). `LobbyState` renders incrementally: `setMessages` on entering a room / reset, `appendMessages` for live messages and catch-ups (follows the bottom only if the user is there or wrote the message — otherwise a "new messages" button), `prependMessages` for older pages with an explicit scroll correction (`overflow-anchor: none` on the list so the browser doesn't apply a second one). The in-game `ChatUI` overlay shows the tail of the same log.
- `GameServer : GameServerBase<GameModel>` owns the fixed **~30 FPS loop** (`PeriodicTimer` at 33 ms). It is a **hosted service** (`IHostedLifecycleService`): the loop starts with the host, and graceful shutdown (SIGTERM/Ctrl+C) closes every socket in `StoppingAsync`, then stops the loop and drops room state in `StopAsync` — no manual `ApplicationStopping` hook. The simulation runs every tick; a `GameTickUpdateEvent` snapshot is sent only every `SnapshotSendEveryTicks`-th tick (default 2 → ~15 Hz; 1 = every tick) via `GameMessenger.BroadcastSpatialUpdates`, which filters recipients by room so only spatial-room members receive movement updates.
- **Tick snapshots are deltas** (`GameTickUpdateEvent`, built on the tick thread): `ServerTimeMs` (sim time, for client interpolation) + `MovementStateData` (`PlayerId`, `X`, `Y`, `AnimationState` byte — 14 B; aim/target/controls/body angle/velocity are no longer replicated) for only the avatars whose position/animation changed within the last `SnapshotRepeatUnchanged + 1` snapshots (default 2 → a stopped avatar's final state is sent 3×), plus a **full snapshot** (every avatar) every `FullSnapshotIntervalSeconds` (1 s; ≤ 0 = always full). Full snapshots go out as **keyframes**: in the latest-wins slot a pending keyframe is replaced only by a newer keyframe, never by a delta, so a client that loses deltas still converges within one full-snapshot period. An avatar absent from a snapshot is unchanged. The one-shot arrays (`DestroyedBulletsIds`, `RespawnedPlayerIds`, `HitPlayersState`) are accumulated over the ticks between snapshots, but still ride the lossy slot (a replaced snapshot loses them; the client currently ignores them). `WsServer.LoadTest` prints tick bytes/sec per spatial client (`--idle 1` = mostly-idle scenario).
- **Client interpolation** (`src/utils/SnapshotInterpolation.ts`, pure + unit-tested): `WsClient` feeds each snapshot into `ServerClock` (server-time estimate from `ServerTimeMs` + arrival time; also estimates the send interval) and each avatar's `PositionBuffer` (`push` for avatars in the snapshot, `hold` for absent ones — no extrapolation; jumps > `TELEPORT_DISTANCE` snap). `GameScene` draws remote avatars at `serverNow − (1.5 × interval + 15 ms)` and our own at `serverNow − (interval + 25 ms)`; velocity (run animation, sprite facing) comes from the interpolated segment. Player input state (`controls`, aim) is client-owned and never overwritten by snapshots.
- **Single-threaded model.** Client requests, connects and disconnects are all queued from socket threads and executed on the tick thread (`GameServerBase` command queue). On connect the client id is reserved atomically and handed to `WebSocketHandler` synchronously (before its receive loop starts); registration, the session, `InitPlayerEvent` (always the client's first message) and the `lobby` auto-join (`JoinRoomResultEvent`, user list, room list) happen on the next tick — no avatar, no game state. A disconnect is queued behind its connect, so a socket that drops early never leaks a session or an avatar. On disconnect `SessionManager` cleans up room membership, removes the avatar (if any) and tells spatial members (`PlayerLeftEvent`).
- Rooms are persistent and defined in `GameServer.InitializeDefaultRooms()` — the built-in ones plus the channels admins created (stored); clients learn them from `RoomListEvent` (id, name, supported modes, persistence, user count, private, created), which leaves out hidden rooms (`Room.IsHidden`: `game`) and private channels the client may not see. Spatial state is filtered. `GameModel` uses plain collections (tick thread only; only the id generators and `PlayersCount`/`BulletsCount` are safe from other threads) — never mutate it outside the command queue. `RoomManager`/`ConnectionManager` stay concurrent (`/info` and shutdown enumerate connections off-thread).
- **Send path** (`WebSocketHandler`): one sender per socket fed by a reliable bounded FIFO (`IClientConnection.Send`; capacity `WebSocketSendQueueCapacity` — overflow **terminates** the connection rather than dropping an event) plus a single latest-wins slot for the tick snapshot (`SendLatest`, used by `BroadcastSpatialUpdates`; keyframe-aware, see above). Order between them is preserved. WebSocket keep-alive pings (`WebSocketKeepAlive{Interval,Timeout}Seconds`, 15 s each) drop half-open connections server-side. For the client side, every connection gets a tiny `HeartbeatEvent` (TypeId 7) every `HeartbeatIntervalSeconds` (5 s; sent on the tick thread via the reliable path, 0 disables), and `WsConnection`'s watchdog treats ~15 s (`WATCHDOG_TIMEOUT_MS`) without *any* message while `open` as a dead socket → normal reconnect/backoff with the banner. The watchdog opens a fresh grace window when its own timer was suspended (frozen tab / sleep) or the tab becomes visible again, so background throttling doesn't cause reconnect storms.
- **Static files** (`Program.cs` → `StaticFileCaching`): Vite's hashed chunks (`/assets/name-HASH.ext`) are served `Cache-Control: public, max-age=31536000, immutable`, `index.html` and `version.json` `no-cache`; unhashed public assets (`/knight`, `/map`, `/ui`, `/assets/logo.png`) get no explicit Cache-Control.
- Everything is wired by `services.AddGameServer(config)` + `app.UseGameServer()` (`/ws`, `/health`, `/info`, `/avatars/{userId}`; `WsServer/WsServer/GameServerHostingExtensions.cs`), shared by `Program.cs`, the LoadTest, the TestClient and the test fixture. `GameServer` is one singleton exposed as both `IGameServer` and the hosted service.

## Gotchas (things that will bite)

- **Folders ≠ namespaces.** Files under `Game/Protocol/Chat/` live in namespace `Game.ServerLogic.Chat.*`; `Shared/` files are in `WsServer.*` / `WsServer.Abstract.*`; rooms are in `WsServer.Rooms`. Match the existing namespace of neighboring files, not the folder path.
- **The server is one project now** (commit "Merging all server projects into one"). References to separate `Game/`, `WsServer.Shared/`, `WsServer.DataBuffer/`, and `BenchmarkSuite1/` projects in `AGENTS.md` are stale — those are now folders inside `WsServer/WsServer/`. (The `Dockerfile` has been updated to the single-project layout.)
- **Two room enums, now aligned.** The server uses `WsServer.Rooms.RoomCompatibility` (`TextChat`, `Spatial`, `VoiceChat`, `VideoChat`) and the client uses `CommunicationMode` (`TextChat`, `Spatial`, `VoiceChat`, `VideoChat`). Stage 2 collapsed the client's old `Spatial2D`/`Spatial3D` into a single `Spatial`, so they're now 1:1 — but they're still **two separate enums**, keep both in sync when adding a mode. (`RoomCompatibility` is `[Flags]`-marked yet its values aren't powers of two — a known latent bug, unrelated.)
- **Rooms come from the server.** `GameServer.InitializeDefaultRooms` (`lobby`, `voice`, the hidden `game`, then the created channels) is the only definition; the client has no room list of its own (`WsClient` syncs `RoomManager` from `RoomListEvent`, requested on every session init and pushed on membership changes; `LobbyUI` renders whatever arrives, with a Play button for any `Spatial` room). Joins are **server-confirmed**: `WsClient.joinRoom()` only sends the request; membership, the spatial mode and the player set change on `JoinRoomResultEvent` (`roomJoined` / `roomJoinFailed` events). The lobby state returns to the *home room* (the room the server auto-joined on connect, `WsClient.homeRoomId`); the game state (re)joins the room whose Play was clicked. The only client-side room ids left are icon lookups in `LobbyUI`.
- **`clientId` ≠ `userId`.** `clientId` is per connection (new on every reconnect; avatars and room membership use it); `userId` is the stable identity (presence, chat authorship, "own" messages). Don't key anything that should outlive a reconnect by `clientId`. Message ids are global across rooms, not per room — gaps within a room are normal.
- **A user key is a device, not a user.** One user can have many keys (each logged-in device has its own), and a key can move to another user (a login reuses it). Never treat `key hash → user` as 1:1 in the other direction; `ClientSession.KeyHash` is the key *this connection* came in with.
- **Game builds must stay off the client's origin.** `GamesOrigin` must be a different origin from every `PortalOrigins` entry (a different host or port) — that is the whole security model of the portal. In production `play.tox.gritsenko.biz` needs its DNS record, a certificate on HAProxy and a route to the same backend, and `GameServer__GamesDataPath` must point outside the release directory (e.g. `/var/lib/wscore/games`) or every deploy loses the builds (`data/games` is relative to the working directory). HAProxy must also let build uploads (`PUT /api/games/{id}/build`, up to `GameMaxBuildMb`) through.
- **Voice needs TURN for some networks, and production has none yet.** STUN alone fails behind symmetric NAT (mobile carriers, corporate networks). `docker-compose.yml` has coturn (profile `turn`, `turnserver.conf`, `.env` written by `scripts/deploy.sh`), but production is the LXC + `wscore.service` deployment (see `AGENTS.md`): there coturn needs its own setup with public UDP ports, and `GameServer__VoiceTurnSecret` / `GameServer__VoiceTurnUrls__0` in the service environment. Testing voice on localhost proves nothing about TURN (host candidates always work).
- **Passwords cross the socket in clear.** `LoginRequest` / `ClaimAccountRequest` carry the password as typed (hashed only server-side), so production must be served over TLS (`wss:`); never log request bodies.
- **Avatars come from the game server, not the page origin.** In dev the page is `:5001` and the images are `:5000` — build the URL with `WsClient.avatarUrl()`, never a relative path.
- **The chat database is local state, not source.** Dev runs write `WsServer/WsServer/data/chat.db` (+ `-wal`/`-shm`; gitignored); in Docker it is the `game-data` volume at `/app/data` (the only path the non-root user can write). Deleting the files wipes history and users, and gives the history a new epoch.
- **MemoryPack `double` for times.** `SentAtMs` / `LastSeenMs` are `double` on the wire on purpose: a C# `long` becomes a TS `bigint` in the generated code.
- Keep `[MemoryPackable]` message types simple (flat, immutable-ish, no complex inheritance) — the serializer and TS generator both assume that.
