# Голосовые комнаты в лобби — оценка объёма работ

Статус: **черновая оценка, имплементация не начата**. Записано по итогам обсуждения 2026-07-08.

## Текущее состояние кода

Голосовой функциональности нет вообще, несмотря на видимость:

- Комната `voice` уже заведена как **пустая запись** — `GameServer.cs:48-53` (сервер), `WsClient.ts:58-59` и `LobbyUI.ts:45` (клиент).
- `RoomCompatibility.VoiceChat` / `CommunicationMode.VoiceChat` — это просто enum-значение для классификации комнаты, никак не подключённое к аудио.
- Проверено grep'ом по всему репо: нет `WebRTC`, `getUserMedia`, `RTCPeerConnection`, `MediaStream`, `Opus`, `AudioContext` — ни на клиенте, ни на сервере.

Значит "имплементация голосовых комнат" — фича с нуля, а не доработка существующего каркаса.

## Архитектурное решение

Два варианта:

1. **WebRTC mesh + сигналинг через существующий WS-канал** (рекомендуется для текущего масштаба). Сервер только пересылает offer/answer/ICE между участниками комнаты через уже существующий `RoomManager`/`IGameMessenger`, сам звук идёт P2P. Подходит для маленьких комнат (~4-6 человек одновременно).
2. **SFU** (mediasoup/LiveKit) — отдельный медиасервер, масштабируется на много участников, но это недели работы и отдельная инфраструктура. Не рассматривается сейчас, но это риск, если комнаты вырастут за ~6 говорящих одновременно.

Оценка ниже — по варианту 1 (mesh).

## Почему TURN обязателен (не опционально)

Изначально предполагалось, что STUN (бесплатный, Google) может хватить — это верно только для localhost/LAN тестирования. Раз сервер работает в реальном интернете, часть пользователей (symmetric NAT, корпоративные фаерволы, мобильные операторы) физически не установит прямое P2P-соединение без relay через TURN. Это не улучшение "для продакшена потом", а обязательный компонент с самого начала.

Хорошая новость: TLS-инфраструктура для secure context (`getUserMedia` требует HTTPS/WSS) уже есть — `nginx.conf` + `docker-compose.yml` уже настроены на Let's Encrypt, и клиент (`WsConnection.ts:194`, `main.ts:8-10`) уже сам переключается на `wss:` по `location.protocol`. Это не добавляет работы.

## Открытый вопрос: хватит ли VPS

У пользователя — VPS у Beget (Москва), заявленный канал 1 Гбит/с.

- **Пропускная способность НЕ является проблемой.** Даже пессимистичный сценарий (10+ человек одновременно в голосовой комнате, все проваливаются в TURN-relay) — это единицы Мбит/с, <1% канала.
- **CPU/RAM тоже не проблема** — coturn просто ретранслирует UDP-пакеты, транскодирования не делает, тянет десятки сессий на 1 vCPU/1GB.
- **Реальная неопределённость — как Beget обрабатывает UDP** на нестандартных портах (DDoS-защита может фильтровать/троттлить короткие UDP-сессии на произвольных портах, что типично для WebRTC ICE). Достоверных данных по политике Beget нет — нужно проверять напрямую, а не гадать по маркетинговым цифрам.

### Как проверить (30–60 минут, до начала имплементации)

1. Поднять coturn на VPS: Docker-контейнер `coturn/coturn`, минимальный конфиг с `use-auth-secret`, открыть UDP relay-диапазон в файрволе Beget.
2. С **двух устройств в разных сетях** (не в одном Wi-Fi) открыть публичный trickle-ICE тестер (webrtc.github.io/samples/src/content/peerconnection/trickle-ice/), вписать туда TURN-сервер и credentials.
3. Проверить, находятся ли `relay`-кандидаты и проходит ли по ним трафик.
4. Если да — Beget не режет UDP на этом порту, можно закладывать TURN как есть.
5. Если нет — нужен `turns:` (TURN over TLS на 443/TCP, почти никогда не блокируется) как fallback — чуть больше конфигурации, но решаемо на том же VPS.

**Это следующий шаг перед стартом имплементации** — снимает единственную реальную неопределённость в оценке.
