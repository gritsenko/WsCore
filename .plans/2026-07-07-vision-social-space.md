# Видение продукта: социальное 3D-пространство для вечеринок

Дата: 2026-07-07. Дополняет [2026-07-07-roadmap.md](2026-07-07-roadmap.md) (этапы 0-4 — фундамент, этот документ — продуктовая надстройка).

## Идея

Единый клиент WsCore — самодостаточный продукт: браузерное 3D-пространство в духе VRChat/Gather/Mozilla Hubs, где участники:

- **бегают по локациям** — готовым (фиксированным) или созданным самими участниками;
- **строят локации прямо в клиенте** — из примитивов и, позже, готовых моделей;
- **говорят голосом с пространственным звуком** — громкость и панорама зависят от взаимного положения аватаров;
- **видят друг друга** — видео с веб-камеры на месте головы персонажа.

Целевой сценарий: **онлайн-вечеринки друзей** — зашёл по ссылке, увидел головы друзей, походил, поговорил в разных углах комнаты разными компаниями.

«VR» здесь — референс к VRChat как жанру, не требование шлема. Поддержка WebXR — возможное будущее (Three.js умеет), не MVP.

## Почему это ложится на существующую базу

| Что нужно продукту | Что уже есть |
|---|---|
| Комнаты-локации, вход/выход, список | `RoomManager`, `GetRoomList`/`JoinRoom`, комнаты с `VoiceChat`/`VideoChat` уже в `RoomCompatibility` |
| Позиции аватаров в реальном времени | Тик-луп 30 FPS + `GameTickUpdateEvent` + spatial-фильтрация `BroadcastSpatialUpdates` (готовый interest management для звука) |
| Строитель | Домен `Map` (`SetMapObject`/`DestroyMapObject`/`UpdateMapObjectsEvent`) — зародыш; сейчас сломан (всегда блок (0,0), аудит §2), фактически потребует нового протокола объектов |
| Персистентность локаций | Интерфейс `IWorldStorage` есть, реализация пустая — становится обязательной |
| 3D-клиент | Решение о едином Three.js-клиенте (roadmap, этап 2) |
| Сигналинг для WebRTC | Существующий бинарный протокол — просто новый домен сообщений `Rtc` |

Ключевое архитектурное свойство: **медиа не проходит через .NET-сервер**. Голос/видео — WebRTC напрямую между участниками (или через SFU позже). Сервер остаётся лёгким: state мира + текстовый чат + сигналинг. Вся стабилизация из этапов 1-2 roadmap — фундамент этого продукта без изменений.

## Ключевые технические решения

### Голос и видео: mesh → SFU

- **MVP — полный mesh (P2P)**: каждый с каждым. Для вечеринки это работает, потому что видео-голова маленькая: 240p@15fps ≈ 200-300 кбит/с на поток, аудио Opus ≈ 32 кбит/с. На 8 участников — ~7 исходящих потоков ≈ 2-2.5 Мбит/с аплоада. Реальный потолок mesh с видео — **6-10 человек**, что и есть «вечеринка друзей».
- **Масштабирование — self-hosted SFU** (LiveKit / mediasoup), когда захочется 15+ или запись. Сигналинг проектировать так, чтобы замена mesh→SFU не меняла клиентский UX.
- **Сигналинг** — через существующий WS-протокол: домен `Game/Protocol/Rtc/` с `RtcOfferRequest/Event`, `RtcAnswerRequest/Event`, `RtcIceCandidateRequest/Event` (адресная пересылка конкретному клиенту — новый паттерн для `GameMessenger`, сейчас есть только broadcast/send).
- **Инфраструктура**: coturn (STUN/TURN) в docker-compose — без TURN часть NAT-пар не соединится; `getUserMedia` требует HTTPS — TLS уже терминируется nginx-сайдкаром (localhost для дева работает без TLS).

### Пространственный звук

Web Audio API: на каждый входящий аудиопоток — `PannerNode` (HRTF), координаты обновляются из `GameTickUpdateEvent`, слушатель — из камеры/аватара. Rolloff по расстоянию → «компании по углам» получаются сами собой. Позже: аудио-зоны (сцена слышна всем, приватный угол — только внутри).

### Видео-голова

`VideoTexture` из `MediaStream` на плоскости/сфере на месте головы аватара. Билборд к камере (как сейчас спрайты в `Player3D`). Fallback без камеры — статичная голова + ник. Обязательные контролы: mute/camera-off, индикатор «кто говорит» (AnalyserNode).

### Строитель локаций

- **Новый протокол объектов** вместо тайлового `Map`-домена: объект = `{id, type (примитив/модель), transform (pos/rot/scale), цвет/материал, owner}`. События: создать/переместить/удалить + полный снапшот при входе в локацию.
- **Клиент**: режим редактирования — raycast-размещение на поверхности, простые гизмо (двигать/вращать/масштабировать), палитра примитивов (куб, сфера, цилиндр, плоскость) и цветов.
- **Сервер**: локация = комната + её список объектов; персистентность через `IWorldStorage` (файл/SQLite на локацию); динамическое создание комнат (сейчас комнаты фиксированы на старте — нужен `CreateRoomRequest`).
- **Права**: владелец локации; режимы «строят все» (вечеринка-стройка) / «только владелец».
- **Модели (после примитивов)**: GLTF из курируемой библиотеки на сервере (не произвольный аплоад сразу — размер/безопасность/модерация).

### Судьба шутерной механики

Рекомендация: **вынести из ядра**. Пули/HP/фраги/респавн не нужны социальному пространству и создают серверную сложность (утечка пуль, коллизии — половина находок аудита §1). После стабилизации (этап 1 — фиксим, пока код жив) и M1 — удалить из `GameModel` тика, оставить движение/позиции/чат. Вернуть позже можно как **мини-игру для вечеринок** (лазертаг в построенной локации — само по себе фичей звучит неплохо), но уже поверх стабильного ядра.

## Майлстоуны (продолжение roadmap после этапов 0-3)

### M1 — Социальное ядро (фундамент готов после этапа 2)
Одна фиксированная локация, аватары с никами, движение, текстовый чат, **ссылка-приглашение** `/?room=<id>` (query-роутинг, который раньше был `?mode=`, обретает смысл).
✅ Критерий: 5 друзей зашли по ссылке, ходят и чатятся, ничего не течёт.

### M2 — Голос с пространственным звуком (M-L)
Домен `Rtc` в протоколе + адресная пересылка, mesh WebRTC (audio-only), `PannerNode`-спатиализация, mute + индикатор речи, coturn в docker-compose, TLS-чеклист.
✅ Критерий: 6-8 человек говорят; отошёл в угол — тех, кто у «сцены», почти не слышно.

### M3 — Видео-головы (M)
Видеотрек 240p в существующие peer-соединения, `VideoTexture` на голове, camera on/off, fallback-аватар, деградация битрейта при слабом канале.
✅ Критерий: вечеринка 6 человек с видео-головами, аплоад каждого ≤ 3 Мбит/с.

### M4 — Строитель локаций (L)
Новый протокол объектов, режим редактирования с примитивами, персистентность локаций, динамические комнаты, права владельца.
✅ Критерий: создал локацию, настроил, перезапустил сервер — всё на месте; друг зашёл по ссылке в неё.

### M5 — Модели и полировка вечеринки (по запросу)
GLTF-библиотека, реакции/эмодзи над головой, аудио-зоны, скриншеринг на «экран» в локации, пароль на комнату, WebXR — по желанию.

## Открытые вопросы (не блокируют M1-M2)

1. Приватность: комнаты по ссылке-секрету или пароль? (для вечеринок достаточно непубличного id в ссылке + пароль опционально).
2. Аккаунты: для M1-M3 хватает ника + токена сессии (roadmap, этап 5.3); владение локациями в M4 потребует чего-то постояннее.
3. Лимит участников и момент перехода на SFU — измерить на реальной вечеринке после M3.
4. Мобильные браузеры: getUserMedia + WebGL работают, но UX управления — отдельная задача.
